# 软件需求规格说明书 — 修仙包

简体中文 · [English](SRS.md)

状态：草稿。本批次落地时取第一个基线。
批次：B18
日期：2026-11-12

本文规定本仓两个包必须做到什么。`REQ-001`–`REQ-015` 描述已发布的行为
（`cultivation@1.0.1`、`cultivation-rogue@0.6.3`）；`REQ-016` 与 `REQ-017` 是 `0.7.0`
的目标，数据尚未落地。
设计落点在 `SDD.md`，测试在 `STP.md` 与 `STD.md`。

## 意图

玩家装一个包，读——或者玩——一个山里宗门的故事。引擎负责跑，本仓只供数据。
所以下面每一条都能从引擎显示的东西、压缩包里装的东西、或者维护者能算的哈希看出来，
而不是从引擎源码里看出来。

## 范围

在内：包是什么（身份、信封、语言），包玩什么（线性阅读、信念、心声、派遣、日程机），
包记住什么（存档、合集），以及一次发布是什么（标签、压缩包、描述文件、CI）。

不在内，也不作为本仓的需求：引擎及其能力；美术、声音与字体（两个包都不带素材）；
别的世界（`lethebar-game-sanguo`）；第二幕的正文量（`0.8.0`，尚未设计）；
`en` 以外的语言本地化。

## 需求 — P1

| ID | 需求 | 验收 |
|---|---|---|
| `REQ-001` | `packs/` 下每个目录打出一个包，其 manifest 的 `id` 与目录名一致，且任意两个包的 id 不同。 | 逐目录构建，每个目录各出一个压缩包；每个包的 manifest id 与其目录名相同；这些 id 互不相同。 |
| `REQ-002` | 可安装的压缩包根上只有 `manifest.json`，其余条目都在 `data/`、`assets/` 或 `i18n/` 下；没有可执行条目、符号链接，也没有 `..` 或反斜线；一个包最多 500 个条目、单条目 4 MiB、合计 32 MiB。 | 检查器接受两个已发布压缩包，并拒绝一份加了第二个根文件、符号链接或超限条目的副本。 |
| `REQ-003` | 包为默认语言和它列出的每种语言各声明一个显示名，玩家看到的是当前界面语言的名字，永远看不到 id。 | 界面在中英文之间切换时，包列表先显示「修仙」再显示 Cultivation，且不出现任何包 id。 |
| `REQ-004` | 包声明的每种语言里，每个节点、每个选项文本、以及引擎可能从包内数据打出的每个标签都有译文。 | 一份英文表缺了一个节点或一个标签的包副本在安装时被拒；两个已发布包都能装上，且能走到的每个界面都显示英文。 |
| `REQ-005` | 线性包从其声明的入口节点开始，选项把本局带到它指向的节点；没有选项的节点结束本局——除非包声明了阶段机，那么没有选项的节点不结束本局。 | 线性包从第一屏开始，走完五个节点后到结束屏；派遣包里，山门节点没有选项，本局仍在继续。 |
| `REQ-006` | 声明了 progress 的包向读者显示本局走到哪里，按已访问节点除以总节点计；包本身不带任何规则。 | 线性包在第二个节点显示「第 2/5 步」；它的规则文件声明零条规则。 |
| `REQ-007` | 派遣包记录两个由选项改变的信念数，第一幕按这两个数收束到四个结局之一。 | 同一幕用相反的回答走两遍，落在不同结局，结束时记录的信念数也不同。 |
| `REQ-008` | 场景可以带第二层文本，只在有听者时出现；有一个选项能改变听者相信的东西。 | 同一场景在有听者和无听者时显示不同文本；选了揭示的局，记录的信念与没选的不同。 |
| `REQ-009` | 派遣包提供六次派遣和一次歇息；每次派遣至少改变一个弟子的伤、信或贪；伤到 2 及以上的弟子不能派出，拒绝时说出理由；歇息能让弟子重新可派。 | 同一弟子往废墟派两次后伤为 2，再派被拒，理由里带出伤这个键；歇息一次后又能派出。 |
| `REQ-010` | 派遣包给一局三十六天、三个年号、每名弟子一条失败；弟子伤到 3 时本局失败，失败语点出是哪名弟子。 | 三十六个动作耗尽天数；弟子伤到 3 时本局以该弟子自己的理由结束，天数计数不再接受动作。 |
| `REQ-015` | 派遣包每十二天翻一年，按田里的收成付石，每进入一年扣一石存粮，并在某一波来临时因墙太矮或米缸见底结束本局。 | 第十三个动作后年份读作 2，且已扣过第一年的存粮；一级田让此后每个动作多一石；进入第二年时墙不足六级，本局以那一年的破墙语结束；某天开局米缸为零，本局以米缸语结束。 |
| `REQ-011` | 每个包存三个槽位，键由包 id 构成；读档回到存档时记下的节点与账本状态。 | 在派遣包存的档只出现在它自己的包里；读回时回到存档时的节点，账本数值一致。 |
| `REQ-012` | 两个包声明同一个合集 id 与同一组合集名，界面因此能把它们归成一个世界。 | 包列表把两个包归在同一个世界条目下；删掉合集块的副本会被单独列出。 |
| `REQ-013` | 一次发布是一个 git 标签 `pack/<id>/v<version>`，带构建好的压缩包和一份记录该包 sha256 的描述文件。 | 对任一已发布标签，下载两个资产并对压缩包求哈希，结果与描述文件里记的值一致。 |
| `REQ-014` | main 前进时逐目录构建并检查信封，被拒的压缩包让构建失败。 | 一个弄坏某个包的提交会让工作流转红；当前 main 在两个包上都是绿的。 |
| `REQ-016` | 在一局里挣到的名字会活过这一局：走到山门仍在的局记下一个名字，下一局带着这些名字换来的好处开局；以失败收场的局什么也不记。 | 走到第三年年底的局让名字数加一，下一局开局就有一块田在种；折了弟子的局名字数不变、下一局开局也不变。 |
| `REQ-017` | 每年的那一波同重：重量来自包声明的抽签，重载本局不会重掷。 | 同一回合走到两次、其中一次经过重载，波重相同，当年的贡也等于这个重量。 |

## 说明

`REQ-006` 是唯一一条描述引擎行为而非数据的需求：步数是引擎按已访问节点算的，
包除了一声「我要 progress」之外没有别的写错方式。这条留着，因为玩家看得见它。

`REQ-004` 比读起来更硬：引擎把缺标签当成致命的安装错误，不是界面瑕疵。
派遣包 `0.2.0` 与 `0.3.0` 正是这样装不上的；`0.4.0` 是第一个补上的版本。

`REQ-015` 是在同一个动作里结算的：引擎依次翻年、付田产、扣存粮、查墙，
所以墙要在跨年的那个动作之前立好；跨年之后再垒的墙救不了那一年。
田产在扣存粮之前，所以一局可以先把最后一石花在田上，再被年份收走。
